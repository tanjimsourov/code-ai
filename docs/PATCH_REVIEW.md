# Patch Review and Apply Modes

Generated patches must be reviewed carefully before they modify your
repository.  This document explains the patch metadata, apply modes
and approval workflow in the Code Editor.

## Patch Contents

A **candidate patch** consists of:

- A JSON payload containing a mapping of relative file paths to their
  proposed contents (`files`), a list of `changed_files` and a
  unified `diff` for human inspection.
- `before_snippets` and `after_snippets` summarising the first few
  lines of each modified file.
- A `risk_level` hint generated by the model indicating whether the
  changes are low, medium or high risk.

The executor also produces a unified diff between the original
repository and the patched workspace when a candidate is selected.
This diff includes newly created files, modified files and deleted
files.  Large or binary files are noted rather than diffed.

## Apply Modes

When a task is created the client can request one of several apply
modes:

- **suggest**: generate a patch and stop.  The patch is persisted
  but not applied automatically.  The task ends in the
  `awaiting_review` status.
- **draft_patch**: similar to `suggest` but the patch is applied
  to the isolated workspace so that tests can run, producing a
  draft.  The repository is not mutated until approved.
- **apply_to_workspace**: apply the patch to the workspace only;
  do not update the canonical repository.  Useful for previewing.
- **auto_apply_if_validated**: automatically apply the patch to the
  workspace and run validation.  If validation passes the task
  completes; otherwise it ends in `validation_failed`.
- **manual_approval_required**: require an explicit approval before
  applying the patch, even if validation passes.

The effective apply mode may be restricted by policy (e.g. sensitive
repositories require manual review).  It is recorded separately on
both the `TaskRun` and each `CandidatePatch`.

## Approval Workflow

Patches generated in suggest or manual approval modes must be
approved before being applied to the canonical repository.  The
approval status is tracked on both the task (`approval_status`) and
the candidate patch.  When a reviewer approves a patch the executor
will apply it to the repository, run a final validation if needed
and update the task status accordingly.  Rejecting a patch marks it
as `rejected` and transitions the task to a terminal state.

All apply, approve, reject and rollback actions are audit logged via
`CodeEditorRequestLog` and associated models.  Only users or API
keys with `CanApprovePatch` or `CanMutateRepository` permissions
should perform these actions.
